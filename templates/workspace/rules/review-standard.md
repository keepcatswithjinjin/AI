# 上线前代码 Review 标准

## 适用范围

当用户提出以下要求时，必须使用本标准：

- 上线前代码 Review；
- 前端/后端上线检查；
- 增量功能影响评估；
- 默认关闭功能的安全检查；
- 生产数据、配置和旧逻辑不受影响的证明。

## Review 边界（先于所有优先级）

- Review 的对象是指定基线与当前代码之间的 **diff**，以及该 diff 直接触及的调用链；开始前必须写明基线（例如目标分支 merge-base、指定 commit 或用户指定范围）。
- 只报告由本次 diff 新引入、放大或直接暴露为上线风险的问题。当前代码是 Review 的事实来源，不把 Review 变成重做需求设计或合并冲突复盘。
- 发现历史遗留问题、无关模块问题或 diff 前已存在的问题时，不纳入本次问题清单、不要求修复，也不以它降低本次结论；除非本次 diff 直接改变了该问题的行为或影响范围。
- 不使用测试分支或其混合内容作为正确性基线。Review 与冲突解决、合并过程核验职责分离；合并过程的事实由发布流程单独处理。

## 一、先判断功能类型

### 1. 增量类功能

在既有页面、接口、数据或流程上增加可选字段、配置、分支、策略或新处理路径。重点不是只证明新增路径能运行，还要证明关闭增量能力时旧路径保持不变。

### 2. 新增类功能

新增页面、接口、配置入口、任务或完整业务流程，原有功能没有对应入口。重点是证明入口、前后端配合、数据处理和异常处理完整。

如果同时存在两类内容，分别按增量类和新增类检查，不得用“新增功能已完成”覆盖旧逻辑影响评估。

## 二、后端 Review 优先级

按以下顺序检查，前一项不通过时不得用后一项抵消：

### P0：不能引入新的阻断性风险

检查：

- 是否存在数据写错、数据丢失、重复扣款、越权、绕过权限或敏感信息泄露；
- 是否改变事务、锁、幂等、消息、回调、支付、金币或结算的安全边界；
- 是否存在空指针、异常吞没、错误重试、死循环或明显性能阻断；
- 是否可能导致生产启动失败、接口大面积失败或历史数据无法处理。

结论必须给出代码文件和行号佐证；不能只写“未发现风险”。

### P1：增量功能关闭时旧逻辑保持不变

仅对增量类功能强制检查：

- 默认配置是否确实为关闭；
- 未配置、空配置、旧配置和关闭配置是否仍进入原分支；
- 原有接口、查询、保存、扣减、状态流转和异常处理是否保留；
- 新字段不存在或为空时是否不会改变旧行为；
- 新增条件是否只包围增量逻辑，没有扩大旧逻辑的执行范围。

### P1.1：上线后现有数据和配置保持正常

仅对增量类功能强制检查：

- 已存在的销售组合、金币配置、订单、订阅或历史记录是否仍按原规则处理；
- 旧数据缺少新增字段时是否可正常读取；
- 现有配置未启用时是否不会触发新增流程；
- 配置缓存、数据库默认值和接口默认值是否一致；
- 前后端对“未启用、空值、缺省值”的含义是否一致。

### P2：新增功能实现完整

仅对新增类功能重点检查：

- Controller/API、参数校验、Service/Logic、数据访问和返回结果是否闭环；
- 正常路径、参数错误、权限错误、数据不存在和重复请求是否有明确处理；
- 事务、幂等、日志和异常语义是否与项目现有方式一致；
- 如果涉及金币解锁，是否验证扣减、重复解锁、余额不足、并发请求和失败回滚。

### P3：功能整体完整

检查本次需求在 diff 中声明的全部后端入口是否实现，不能只验证主流程而遗漏配置、查询、保存、回滚或兼容路径。

## 三、前端 Review 优先级

### P0：没有引入新的阻断性 Bug

检查：

- 页面是否无法打开、白屏、死循环或无法提交；
- 原有表单、弹窗、列表、筛选、详情、权限和跳转是否被破坏；
- 接口异常、空数据和慢请求是否导致页面状态卡死；
- 新增字段是否导致旧接口返回时渲染异常。

### P1：增量类功能不影响原有页面逻辑

重点检查：

- 增量开关关闭时，原有按钮、表单、弹窗和提交流程是否完全保持；
- 未返回新增字段时，页面是否仍按旧方式展示；
- 新增条件渲染是否只影响新增区域；
- 原有校验、默认值、清空、取消、分页和刷新逻辑是否保持。

### P2：新增类功能实现完整

重点检查：

- 页面入口、路由、组件、请求、状态、成功反馈和错误反馈是否闭环；
- 表单、弹窗、列表、详情、空态、加载态、错误态和权限态是否覆盖；
- 前端提交字段、后端接收字段、枚举值和默认值是否一致；
- 配置默认关闭时，页面是否展示正确的默认状态。

## 四、前后端共同检查

- 配置名称、默认值、枚举、字段类型和空值语义一致；
- 前端只在后端实际支持时展示新增入口；
- 后端未启用时，前端不会误显示已生效；
- 接口失败时，前端不会把失败显示成成功；
- 现有数据和新配置同时存在时，不出现重复、覆盖或状态错乱。

## 五、证据要求

每个核心结论至少提供一种直接证据：

- `文件绝对路径:行号`；
- 关键条件分支或默认值的短代码片段；
- 前端组件/路由/请求调用链；
- 后端接口/服务/数据访问调用链；
- 配置关闭和开启时的实际验证结果。

报告中的“未引入问题”“旧逻辑保持”等结论，只能覆盖本次 diff 直接触及的路径；不得扩大为对整个项目历史质量的断言。

### 5.1 影响面穷尽性证据

当结论包含“已找全”“无其他调用点”“未影响其他逻辑”或等价表述时，除上述代码证据外，还必须提供完整检索证据：

- 写明搜索根目录、pattern、文件范围，以及是否包含 `.gitignore` 忽略文件；
- 已加载 FastCtx 时，优先使用 `head_limit: 0` 单次获取完整结果。若返回 `Partial`，先按目录、文件类型或更精确 pattern 拆分为可单次完成的检索；不得以 `head`、输出截断或局部样本替代完整扫描；
- 仅当目标目录在检索全过程没有写入时，才可使用 offset 跨页至 `Complete`；此时记录扫描对应的 commit 或工作区状态。`Complete` 只证明一次遍历完成，不等于跨多次调用取得了同一代码快照；
- 若确需检索生成代码、构建产物或日志，明确改用 `rg --no-ignore`，并说明这些文件是否纳入结论范围；
- `summary` 的 occurrences（匹配次数）不能作为 content 分页 entries（匹配行）的翻页目标；只以实际终止信号判定检索完成。

不能使用以下内容作为唯一证据：

- “代码看起来没问题”；
- “没有修改其他文件”；
- “测试通过”；
- Agent 自己的主观判断。
