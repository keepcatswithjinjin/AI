# 设计阶段约束

> 本文件被 CLAUDE.md 和 AGENTS.md 路由引用。

---

## 方案必须包含的章节

`spec/design.md` 是用户唯一需审核的决策摘要，按以下内容组织；不适用项省略：
1. **目标与边界**：业务目标、可见变化及明确不改项。
2. **方案与关键决定**：已选做法、必要理由与需用户决定的取舍，不穷举替代方案。
3. **影响与协作**：涉及项目、关键接口/数据语义、旧路径兼容及实际依赖，不假设前后端一一对应。
4. **DDL**：结构变化的目标库表、完整拟执行 SQL 及用途，必要的默认值、空值、索引和旧数据语义。未核实项标待确认；DML 不混作 DDL，列出 SQL 不代表授权执行。
5. **发布站点与推荐顺序**：从真实启动类/应用入口、调用链与打包依赖定位，只列需发布的受影响应用及理由；前端按实际构建入口核对。说明顺序、可并行项及适用 DDL 时点，未核实则标待确认。

关键业务决定和默认值必须在 design 可见，不能藏在链接中。完整接口字段归契约，实施与验收验证归计划，进度与停点归交接；不要求“验收与上线风险”章节，不堆排错历史。

---

## 接口设计原则

- **自包含**：接口契约必须完整，不依赖外部 Swagger 链接或文档地址
- **显式枚举**：所有枚举字段必须列出每个值及其含义，禁止写"见代码"
- **必填标注**：每个字段必须标注是否必填
- **向后兼容**：接口变更必须考虑已有调用方的影响

## 文档产出规范

每个复杂需求产出技术设计方案：

- 保存路径：`__WORKSPACE_ROOT__\briefs\[cross|backend|frontend]\[需求标识]\spec\design.md`，需求根 README 导航到当前文档与 runtime。
- 按实际角色维护 `spec/backend-plan.md`、`spec/frontend-plan.md`，不强建另一端空计划。

需求根 `README.md` 必须按 [需求 README 模板](brief-readme-template.md)生成并校验链接，先路由到 [工作站 执行入口](execution-entry.md)，再导航本需求实际存在的 spec 与 runtime。README 不复制公共角色、编码风格或工具说明；不为填满模板创建空文档。该要求在实际产出方案时执行，不改变新建登记阶段不预建模板的约定。

执行权限及编码风格按 [执行入口](execution-entry.md)路由，不复制公共规则。计划按行为拆任务，代码路径是核实过的定位线索，不预先规定全部方法拆分；与源码不符时核验真实入口，不盲改。

多项目按位置 ID 分节，必要时才拆位置级计划；有依赖写前置条件、产出和消费者，无依赖可分别执行。不默认后端先于前端，不从角色或分组推断关系。

每个 `*-plan.md` 按下面顺序组织；不适用项省略，不填空模板：

1. **执行前核对**：关联的 `spec/design.md`、适用的 `spec/api-contract.md`，以及需要在源码中核实的入口与当前行为。
2. **不可改变的约束**：旧路径、默认关闭行为、旧数据/空值语义、明确排除的项目或链路。
3. **实施任务**：修改目标、已核实入口、预期行为、保留边界、必要联动与依赖。字段引用契约，只说明读写位置和处理行为。
4. **验证场景与证据**：选择相关场景，写前提/输入、预期结果和需保留的旧行为；不只列场景标签。已核实的测试和构建入口可引用，未确定的按项目规则选择，不预写所有测试方法。
5. **完成检查**：对照当前 diff 检查目标、契约与未改边界；发生设计变化时按 `rules/task-lifecycle.md` 第八节回写。

计划应减少业务猜测，而非替 Agent 编写全部代码；未核实内容明确标注，不以篇幅代替清晰约束。

执行中方案发生变化时，执行 Agent 按 `rules/task-lifecycle.md` 第八节同步最新事实；`spec/design.md` 保留原方案到当前决定的简短变化说明、原因和影响，供用户只审核本文件。不要把执行进度、长篇排错记录或会话历史堆入设计。

大范围删除或重写方案前说明涉及范围，由用户决定是否保留旧版本；默认不创建快照，禁止自行生成 `.bak` 等备份，见 `rules/task-lifecycle.md` 第九节。当前文档放需求 `spec/`，执行材料按第十节归入 `runtime/`。

## 前端方案解释要求

前端计划只解释本需求新增或改变的实现；沿用既有选型时指出复用入口，不默认逐项教学：

- **组件选择理由**：为什么用这个组件，不用其他替代方案
- **状态管理方案**：数据如何流转，哪些放 Pinia、哪些放组件内
- **接口调用方式**：在哪里发起请求，错误如何处理
- **路由与页面结构**：页面如何组织，路由如何配置
- **关键代码示例**：文字不足时才给短例，不预写全部实现

禁止仅给出技术术语堆砌（如"使用 Vue3 Composition API + Pinia 管理状态"），必须有可执行的具体指引。

## Subagent 使用规范

当需求满足以下任一条件时，应启用 Subagent 并行处理：

- **跨项目探索**：需要同时了解前后端或多个后端项目的已有实现
- **独立子任务**：需求涉及多个可独立处理的子模块，互不依赖
- **广度搜索**：搜索范围跨越 3 个以上项目

资源分配按实际需求判断：探索任务用 `Explore` 类型，方案设计用 `Plan` 类型，前后端协作时两端探索可并行启动。

**不适用场景**：单文件修改、已知路径的精确查询、简单逻辑调整。

## 前后端协作规范

### cross 单 Agent 双角色

cross 需求默认由同一个 Agent 承担后端角色与前端角色；即使代码仓库前后端分离、存在两个 worktree，也不默认拆分为两个 Agent。

通用角色职责不写入每个 brief，固定维护在：

- `__WORKSPACE_ROOT__\rules\backend-role-guide.md`
- `__WORKSPACE_ROOT__\rules\frontend-role-guide.md`

计划只写需求特有的任务、约束、依赖和验证；字段引用契约，不重复维护。

### 契约优先

存在前后端接口协作时，双方通过 `spec/api-contract.md` 协作；它是字段级接口定义的**唯一真相源**，`spec/design.md` 保留供人工审核的关键接口语义摘要：
- 后端开发依据契约实现接口
- 前端开发依据契约对接接口
- 契约变更由确认该变化的 Agent 同步更新 `spec/api-contract.md` 与 `spec/design.md` 摘要，不要求重新开启 design session；未经确认的业务取舍不得自行写成已定方案

### 协作流程

```
1. 需求评审（人）：确定前后端配合点
2. 接口设计（本 design session）：产出 api-contract.md
3. 执行开发（同一 Agent）：按 backend-role-guide 与 frontend-role-guide 依次处理后端/前端
4. 联调核对（同一 Agent + 人）：核对契约、字段、交互和测试环境结果，问题反馈回到步骤 2
```

### 契约维护

- 契约文件与设计方案同目录，命名固定为 `spec/api-contract.md`
- 枚举值、字段必填性变化 = 契约变更，必须更新文档
- 后端完成接口后，Swagger 可作为辅助验证工具，但非权威来源

### 设计方案存放规则

```
briefs/
├── cross/<需求名>/spec/      # design.md + api-contract.md + backend-plan.md + frontend-plan.md
├── backend/<需求名>/spec/    # design.md + backend-plan.md
└── frontend/<需求名>/spec/   # design.md + frontend-plan.md
```
