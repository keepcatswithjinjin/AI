# 改动检查报告规范

> 本文件定义面向开发者/负责人的改动检查报告写法。它不面向测试同事，重点是帮助确认 Agent 是否越界、是否只改了当前需要改的地方、是否影响旧逻辑。

## 一、适用场景

当用户要求生成以下内容时，必须读取本文件：

- 检查报告
- 改动范围报告
- 影响范围说明
- 证明没有改其他逻辑
- 前端改动说明
- vibe 前端检查
- 给我看改了哪里

## 二、写作原则

- 不需要复述需求背景；用户已经清楚需求。
- 直接说明改了什么、没改什么、怎么证明。
- 可以出现文件、页面、入口、接口、字段、组件等信息，但不要写成大段源码讲解。
- 对前端 vibe 修改尤其要强调边界证明：不能只说“没影响”，必须给依据。
- 如果无法证明未影响旧逻辑，必须明确写“无法完全证明”，并给出建议回归范围。

## 三、必须包含

```markdown
# 改动检查报告

## 1. 改动范围
- 改动文件：
- 改动页面/入口：
- 改动接口/字段：
- 未改动范围：

## 2. 改动后的变化
- 原本行为：
- 现在行为：
- 用户/后台可感知变化：
- 如果只是兼容性改动：说明功能本身没变，只是兼容某种返回、空值、历史数据或边界情况。

## 3. 未改变的原有逻辑
- 原有主流程是否保持：
- 原有入口是否保持：
- 原有查询/保存/提交/按钮/权限是否保持：
- 原有接口入参/出参是否保持：
- 原有数据处理是否保持：

## 4. 证明依据
- 通过代码触及范围证明：
- 通过未修改文件证明：
- 通过页面/接口入口证明：
- 仍无法证明的点：

## 5. 风险和建议
- 可能受影响的地方：
- 建议回归范围：
- 需要人工确认的点：
```

## 四、兼容性改动说明

如果本次代码调整是兼容性改动，必须明确拆开说明：

- 功能本身是否属于本次需求；
- 兼容的是哪种返回、空值、历史数据、异常状态或边界情况；
- 原主流程是否保持不变；
- 为什么该兼容不会改变原功能行为；
- 仍建议回归哪些入口。

示例写法：

> 本次没有改变原页面主流程，只是在接口返回缺少某字段时增加兜底展示。原查询、保存、按钮权限、跳转逻辑未修改。由于代码触及了该页面展示链路，建议按低重要性回归该页面入口和正常展示流程。

## 五、输出边界

- 不写测试同事视角的详细测试步骤；测试同事说明走 `rules/tester-note.md`。
- 不用“应该没有影响”这种模糊说法；要么给依据，要么标记无法完全证明。
- 不扩大到未触及模块。
- 不把开发自测结果当作“没有影响”的唯一依据。
