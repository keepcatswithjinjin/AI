# 阶段交接与中断接续规范

> 供不同客户端、CLI 和模型接续同一需求。交接保存当前停点和证据，设计决定仍以最新 spec 为准。

## 一、自动维护时机

- 已有需求 brief 的任务，每完成一个有意义的阶段，Agent 必须自动创建或更新 `runtime/agent-guide.md`，无需询问用户。阶段指可独立说明结果的工作单元，例如方案交付、一个模块实现、后端或前端实施、一次验证；不是每次工具调用或每条消息。
- 暂停任务、遇到阻塞、准备切换 Agent/客户端或结束执行对话前，即使阶段未完成，也必须更新当前停点；较长阶段中完成可接续的子任务后及时记录，不等整项任务或额度耗尽才维护。
- 阶段完成先更新交接，再回复阶段结果或继续下一阶段；无需为了交接而中断已获授权的后续工作，也不需要反复请求写文档授权。
- 纯问答、没有执行进展的状态查询和默认只读的独立 Review 不因本规则自动写文档。用户明确要求保存 Review 接续信息时再维护，不改写实现阶段的完成事实。
- 未建立 brief 的简单需求，或本次明确授权跳过 briefs 的任务，默认在阶段回复提供同样要点的简短交接摘要，不为交接强建 brief、登记复杂需求或推进状态机。用户已指定持久化位置时直接在该位置维护；其他新增容器仍按 `rules/task-lifecycle.md` 第十节处理。
- 客户端退出、限额或进程中断可能导致 Agent 无法再写入；交接只表示最后一次已核验的检查点，不能承诺覆盖突发中断后的所有变化。写入失败时在回复提供可接续摘要并说明未落盘，不声称已更新。

## 二、位置与维护方式

- 标准路径为 `__WORKSPACE_ROOT__\briefs\<类型>\<需求>\runtime\agent-guide.md`；已授权需求的 runtime 可按固定目录模式创建，不预建空文件。
- 始终维护同一份当前交接，更新停点、进度、验证和下一步，移除已解决阻塞；保留仍有效的证据及未完成事项，不追加完整聊天流水。
- 历史 `需求-agent-guide.md`、`handoff-agent-guide.md` 兼容读取；下次实际维护时使用标准文件名，不主动批量迁移或删除旧文件。
- 更新前先读取现有交接与本次相关 spec，保留其他执行者仍有效的信息；发现并行修改或事实冲突先核验，不用自己的旧摘要覆盖新内容。
- 已确认的方案变化先按 `rules/task-lifecycle.md` 第八节更新 design、契约或计划，再在交接中链接对应章节；待确认提议单列，不能写成已定方案。

## 三、最低交接内容

按以下结构简洁维护；不适用项写“无”，未核验项明确写“未核验”，不要为填满模板编造内容。

```markdown
# [需求名称] - Agent 交接指南

## 资料导航
- [需求入口](../README.md)
- 当前设计、适用契约和计划：链接 ../spec/ 下实际存在的文件及相关章节。
- [代码位置与分支索引](../../../WORKTREE-INDEX.md)：当前定位入口，接手时再核验实时 Git。

## 当前停点
- 更新时间：YYYY-MM-DD HH:mm（时区）
- 当前阶段与状态：进行中 / 阶段完成 / 阻塞 / 任务完成
- 停在：具体任务、文件或步骤；若完成则说明下一阶段。
- 停止原因：阶段交付 / 等待决定 / 环境问题 / 主动交接等。
- 下一步第一件事：可直接着手的动作；若需决定，先写待决定的问题。

## 已完成与未完成
- 已完成：实现结果；区分已修改、已提交、已发布、已验证。
- 未完成：待做项、半成品与已知问题；说明涉及的关键文件或模块，不复制整份 diff。

## Git 现场（记录时证据）
- 检查时间：...
- 每个涉及的业务仓库分别记录：仓库标识、当时分支、完整 HEAD 提交号。
- 未提交现场：暂存 / 未暂存 / 未跟踪的相关文件及用途；区分本任务与已知无关改动。
- 正在合并、冲突或其他 Git 操作：无 / 当前状态及继续入口。
- 以上是记录时状态，接手时必须重新核验；当前路径与分支定位以全局索引及实时 Git 为准。

## 验证证据
- 每项记录：验证内容、实际命令或证据链接、执行目录/模块、对应 HEAD 与未提交改动范围、结果。
- 结果区分：通过 / 失败 / 未运行 / 运行中；失败说明原因，运行中说明如何查询。
- 后续代码变化使哪些验证失效、还需要补跑什么：...

## 决策变化与阻塞
- 已确认变化：链接已更新的 design/contract/plan 章节及简短原因，不另立方案结论。
- 待确认问题与提议：说明影响和需要用户决定的内容，不当作执行授权。
- 已知失败及排查证据：只记能帮助接续的结论，避免下一位重复尝试相同失败路径。
- 仍在运行的构建或外部任务：标识、状态查询方式；若依赖原客户端进程，注明无法保证跨客户端继续运行。

## 下一个 Agent 接入步骤
1. 读取当前需求 README、最新适用 spec 和目标项目规则，再读本交接。
2. 核验涉及仓库的实时 Git 状态与代码；对照记录确认新增变化、未提交现场和验证是否仍有效。
3. 从“下一步第一件事”继续；存在未确认决定时先处理该决定，再执行受影响部分。
```

## 四、Git 与证据边界

- Git 现场指本次修改代码所在的业务仓库，通常是需求 worktree；单次授权在根项目执行时记录该根项目仓库。跨项目逐仓库记录。工作站 根仓库只用于工作站规则/工具维护，不能代替业务仓库的记录。
- 使用只读 Git 查询核实，例如 `git status --short`、`git branch --show-current`、`git rev-parse HEAD`，需要理解改动时再读暂存区及工作区 diff；detached HEAD 如实注明。
- “Git 现场”仅是文字证据，不执行 commit、stash、切分支、复制源码或创建备份。提交、发布和删除仍遵守各自授权。
- 路径与当前分支的唯一定位入口仍为全局 WORKTREE-INDEX 和实时 Git；交接中允许记录带时间的当时分支、提交号与现场作为历史证据，不作为第二份动态索引。
- HEAD 未变也不代表代码未变：验证若基于未提交代码，必须说明相关改动；接手时核验差异，无法确认验证覆盖当前代码时标记需重验，不沿用“已通过”。
- 若接手时状态与交接不同，先检查新增提交、diff 和最新 spec，解释差异后继续；不为匹配交接而回退或覆盖代码。

## 五、写作与收尾

- 接续所需信息必须能从当前文件及有效链接获得，不依赖原聊天、客户端会话 ID 或模型记忆。不记录凭据、令牌、完整日志或无关业务数据。
- 创建或更新后核验导航链接存在，并确认停点、未完成事项和验证结果没有互相矛盾；回复中简短指出已更新的交接路径。
- 默认不创建文档快照或 `.bak` 备份；大范围删除有效旧内容仍遵守 `rules/task-lifecycle.md` 第九节。常规检查点更新无需询问。
- 纯 Markdown，可跨客户端和 CLI 使用；本规范只约定 Agent 行为，不代表已部署自动写入程序或后台定时任务。
