# 后端编码习惯

> 本文件沉淀多项目工作站中通用的后端编码习惯。项目级 `AGENTS.md` / `CLAUDE.md` 与当前源码始终优先；本文件不替代项目特有架构规则。

## 一、编码前检查

- 修改前重新读取目标文件，以当前源码作为唯一基线。
- 先检索现有类似实现，包括 Controller、Biz、Logic、Service、Mapper、DTO、枚举、常量、测试类和配置。
- 优先复用已有工具类、枚举、常量、转换方法和异常处理方式。
- 只修改当前任务直接相关代码；发现旁路问题时记录风险或待办，不做机会主义重构。
- 用户在交互中手动修改的代码优先级最高，不得隐式回滚或用历史版本覆盖。

## 二、Java 基础风格

- Java 类引用优先使用 `import` 后的短类名，禁止在方法体、字段声明、参数类型中直接写全限定类名。
- 仅当两个不同包下存在同名类冲突时，允许对冲突类使用全限定名。
- 业务状态、类型、来源、渠道、场景等数字或字符串值，优先使用项目既有枚举或常量；不要直接写魔法数字。
- 新增枚举或常量前必须先查找项目既有位置；不确定枚举值含义时询问用户，不自行推断。
- 注释只写在关键边界、复杂流程、事务/数据源/MQ/权限/支付等容易误用的位置；默认使用中文，除非局部项目风格不同。

## 三、分层与调用

后端分层以当前项目约定为准，通用倾向为：

```text
Controller -> Biz -> Logic -> Service -> Mapper -> SQL
```

- Controller 只做入口适配、参数校验和响应封装，不承载复杂业务逻辑。
- Biz 负责跨 Logic 编排；不要绕过 Logic 直接堆数据访问逻辑。
- Logic 承载业务规则、数据转换、状态流转、多表写入、外部调用编排和事务边界。
- Service 负责单表 CRUD、Mapper 包装或项目既有数据访问抽象；不要把业务规则下沉到 Service。
- Mapper / XML / 原生 SQL 只在 MyBatis-Plus、MPJ 或项目既有查询方式无法清晰表达时使用。
- 如果严格分层会导致明显过度设计，可以按项目既有风格灵活处理，但必须保持调用意图清晰。

## 四、查询与分页

- 简单单表查询优先复用项目既有 Logic / Service 查询方法。
- 多表关联优先遵循项目既有 MPJ、Mapper 或仓储模式；不要为了个人偏好引入新查询框架。
- 分页查询必须使用项目标准分页组件或数据库分页；禁止在 Biz/Logic 中用 `stream().skip().limit()` 做业务分页。
- 原生 SQL 适用于复杂子查询、数据库特定函数、性能优化或现有框架难以表达的场景；使用前先确认项目已有类似写法。

## 五、数据源、事务与逻辑删除

- 涉及多数据源时，必须先确认当前模块、目标表和项目既有 `@DS` / 数据源路由方式。
- 不要随意在一个库的模块中直接注入另一个库的 Service；优先通过对应库已有 Logic / Biz 暴露的方法调用。
- 当前架构若没有跨库事务支持，应避免把跨库写入放进一个隐含事务里；必要时记录补偿、幂等或人工确认点。
- 项目启用逻辑删除时，遵循项目既有逻辑删除处理方式；只有恢复、唯一键冲突、历史数据修复等特殊场景才考虑绕开默认拦截。
- 外部调用、MQ 发送、支付、回调等副作用操作不要随意放入事务内部；优先参考项目既有后置发送、补偿或幂等模式。

## 六、对象构造与方法结构

- 主流程保持高层编排，不堆逐字段赋值、复杂初始化和嵌套转换。
- 复杂对象构造、重复字段赋值、嵌套映射、可复用校验或格式化逻辑，应提取为语义明确的方法。
- 命名倾向：
  - `buildXxx(...)`：构造待持久化或待发送对象；
  - `createXxx(...)`：创建新的领域对象；
  - `assembleXxx(...)`：组装多个来源的数据；
  - `convertToXxx(...)`：类型或层级转换。
- 方法名描述业务目的，而不是泛泛写 `handleData`、`processInfo`、`doBuild`。
- 提取方法只服务于当前改动的清晰性；不要借机重写无关结构。

## 七、提交与输出边界

- 不主动提交、合并、推送；只有用户明确要求时才执行。
- 提交、合入测试/集成分支、推送等操作优先使用工作站受控脚本，禁止手写 checkout / merge / push 流程绕过脚本。
- 完成后说明修改文件、核心差异、影响接口/数据/状态、验证结果和未验证边界。
- 不要把大段 diff 直接贴入回复；除非用户要求，优先给可读摘要和关键位置。
