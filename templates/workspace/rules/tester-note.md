# 测试同事说明规范

> 本文件定义执行 Agent 在需要给测试同事输出功能测试说明时的写法。它不是专业测试方案，不扩大测试边界，只帮助测试同事快速知道测哪里、为什么测。

## 一、适用场景

当用户要求生成以下内容时，必须读取本文件：

- 测试文档
- 测试要点
- 给测试同事的说明
- 功能测试说明
- 回归测试范围
- 提测说明

## 二、写作原则

- 拒绝专业术语，尽量用业务和页面语言说明。
- 保持简洁，不写长篇技术实现，不展开无关边界。
- 只围绕本次代码实际触及的功能、入口和影响范围。
- 讲清楚“原本是什么样”“现在改了什么”“测试从哪里进”。
- 不把单元测试、构建命令、类名、方法名、SQL 细节当作测试同事的主要信息，除非用户明确要求。

## 三、必须包含

```markdown
# 测试说明 - <需求名或功能名>

## 1. 原本现状
- 原来用户/后台/系统看到或操作时是什么表现。

## 2. 本次修改
- 这次改了什么用户可感知的行为。
- 如果只是兼容或兜底，也要说明“功能入口没变，只是处理某种异常/历史数据/边界情况”。

## 3. 测试入口
- 页面入口：
- 操作路径：
- 需要准备的数据：

## 4. 重点验证
- 验证点 1：
- 验证点 2：
- 验证点 3：

## 5. 回归范围
- 回归重要性：高 / 中 / 低 / 不需要
- 原因：
- 建议回归：
```

## 四、回归范围判断

### 4.1 需要回归

只要代码触及了某条功能链路，即使本意只是兼容、兜底、字段补充或小改动，也要根据影响大小标明回归重要性。

| 重要性 | 判断标准 | 写法 |
|------|----------|------|
| 高 | 触及支付、结算、登录、权限、订单、状态流转、核心接口、批量任务、MQ/回调等关键链路 | 必须回归主流程和异常/边界场景 |
| 中 | 触及常用页面、列表、表单、筛选、详情、导入导出、配置保存等普通业务链路 | 回归本入口主流程和相关展示/保存 |
| 低 | 只触及展示文案、非核心字段、兼容兜底、低频分支，且不改变主流程 | 回归本次入口和一个正常主流程即可 |

### 4.2 不需要回归

只有在整个代码线完全没有触及对应功能时，才写“不需要回归”。

示例：

- 本次没有改到该页面、接口、任务、配置或共用组件。
- 本次只改了文档、注释、测试代码，未影响运行代码。

不要因为“功能逻辑看起来没变”就写不需要回归；只要代码触及了这条链路，就应给出低/中/高的回归建议。

## 五、输出边界

- 不主动补充测试环境、账号、数据构造方式，除非本次需求已明确给出。
- 不要求测试同事验证未触及功能。
- 不把开发自测结果包装成测试结论。
- 如果入口不确定，写“入口待确认”，不要猜。
- 如果影响范围不确定，写“建议按中等重要性回归”，并说明不确定点。
